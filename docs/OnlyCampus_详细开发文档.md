# OnlyCampus 校园博客管理系统详细开发文档

> 2026年10月31日界面修订：当前实现采用内容优先的社交平台布局。本段替代下文旧版首页介绍区、卡片式入口和页面导航的视觉安排；角色权限及文章业务流程不变。
>
> 桌面端左栏固定，中栏统一承载首页、探索、搜索结果、文章详情、收藏和个人主页；右栏展示搜索、分类及专栏。探索与搜索结果页把搜索框放在中栏顶部，同时隐藏右栏搜索框并使其余内容上移。手机端使用底部导航。
>
> 首页、搜索结果和作者主页共用帖子预览组件，展示作者、日期、标题、摘要及评论入口；点击正文进入详情，不再显示“阅读全文”和分类标签。搜索结果移除重复筛选表单，用“最新／最近更新”切换排序。
>
> 搜索历史仅存当前浏览器，支持选择、删除及清空。新增 `GET /api/trends` 与 `search_terms` 表，榜单按关键词搜索请求累计次数排序，尚未做用户去重；无记录时显示空状态。组员更新代码后执行 `npm run db:init` 创建新增表，再启动开发服务。该初始化命令同时包含演示数据，仅用于本课程开发数据库。

## 1. 项目目标与范围

### 1.1 设计依据

题目文件《2627-1 题目.docx》对第四题的要求为“设计内容自拟，设计重点自拟，题目范围内自由发挥”。本方案参照前三题的角色权限、数据维护、业务流程、特色交互与统计扩展规模制定。本文中的功能、技术方案、页面数量和验收规则均为小组拟定的实施方案，不代表教师额外规定。

系统名称为“OnlyCampus”，寓意“为校园而生的博客”，面向大学生记录课程学习、项目实践、校园生活和旅行见闻。用户发布博客，并将相关文章组织为成长专栏；读者检索、阅读、评论、收藏；管理员审核内容、维护分类、管理账号并查看平台数据。

核心展示场景：作者建立“我的第一个网页项目”专栏，连续发布需求分析、页面设计、开发过程与成果复盘，形成可以按章节或时间线浏览的成长记录。

### 1.2 本次交付边界

本次做到进阶版，以下内容全部纳入正式验收：

- 注册登录、账号状态与角色权限。
- 文章编辑、服务器草稿保存、发布审核、驳回重提、撤回修改及下架。
- 首页精选、分类标签筛选、关键词搜索及分页。
- 文章目录、阅读进度、专注阅读模式和移动端适配。
- 评论及单层回复、收藏、个人公开主页。
- 成长专栏管理、章节排序、目录与时间线切换。
- 用户管理、公共分类和标签管理、内容审核及评论处理。
- 管理员数据概览、近7日发布趋势图。
- 评论、回复、审核结果及文章下架的站内通知，含未读数和已读管理。

明确不实现：浏览器本地草稿恢复、自动保存草稿、复杂文章版本库、私信聊天、关注系统、支付打赏、AI写作、个性化推荐、定时发布、邮件或短信通知。草稿仅通过“保存草稿”按钮写入服务器；未保存离开编辑页时提示用户。

### 1.3 完成标准

三个模块使用同一数据库、同一身份体系和同一套视觉规范。必须打通“创作—审核—公开阅读—互动—通知”完整流程。不得用固定数组、虚假成功提示或纯前端角色切换替代真实功能。

### 2.2 接口协作约定

先提交数据结构和接口草案，再开发页面。公共字段变动应同步本文及数据库迁移文件。联调期间使用同一份种子数据。接口未实现时可以临时模拟，但验收前必须切换到真实接口并清除演示用权限绕过。

## 3. 技术实现基线

本方案暂按以下技术栈组织目录和接口；若课程明确指定其他技术，可整体替换实现层，业务规则与验收标准保留。

| 层次 | 选定方案 | 实施约定 |
| --- | --- | --- |
| 前端 | Vue 3、Vite、Vue Router | 单页应用，按业务模块组织页面 |
| 样式 | CSS变量、Flex、Grid | 自定义统一视觉样式，避免混用多个组件体系 |
| 服务端 | Node.js、Express | REST API，控制器、业务服务、数据访问分层 |
| 数据库 | MySQL | 使用外键、唯一约束、事务及数据库迁移 |
| 数据访问 | 参数化SQL | 禁止将用户输入直接拼接进SQL |
| 文章编辑 | Markdown文本编辑和预览 | 只做一种编辑方式，禁用原始HTML并过滤输出 |
| 图表 | ECharts折线图 | 展示近7日首次发布数量，附数值表 |
| 登录 | 服务端Session、HttpOnly Cookie | 持久化Session；退出和禁用时使会话失效 |
| 图片 | 服务端本地上传目录 | 数据库存相对路径，禁止把图片Base64放进文章字段 |

项目开始时选定依赖版本并提交锁文件，三人使用相同环境版本。开发端通过代理访问API，部署时前端和API同源。开发过程中不依赖收费服务或外部AI接口。

## 4. 角色与权限

| 操作 | 游客 | 注册用户 | 管理员 |
| --- | --- | --- | --- |
| 浏览公开文章、公开专栏、作者主页 | 允许 | 允许 | 允许 |
| 评论、回复、收藏 | 要求登录 | 允许 | 不提供创作互动入口 |
| 创建文章、管理自己的文章和专栏 | 不允许 | 允许 | 不允许 |
| 查看私人草稿、驳回原因 | 不允许 | 仅本人 | 因审核需要可查看相关内容 |
| 审核、下架、设置精选 | 不允许 | 不允许 | 允许 |
| 修改他人正文 | 不允许 | 不允许 | 不允许 |
| 分类标签、账号、评论治理 | 不允许 | 不允许 | 允许 |
| 读取个人通知 | 不允许 | 仅本人 | 仅本人 |
| 查看平台统计 | 不允许 | 不允许 | 允许 |

管理员为专用账号，不同时承担作者角色。普通用户注册时服务端固定角色为USER，忽略或拒绝客户端传入的管理员角色。演示管理员由初始化脚本创建。普通管理员不能禁用自己或其他管理员。

账号禁用后，现有Session立即失效，后续写操作被拒绝；原有公开文章仍保留，违规内容由管理员单独下架。恢复账号后需要重新登录。

前端路由守卫只控制页面入口，后端必须独立验证登录、角色和资源归属。用户不能通过修改请求中的文章ID、专栏ID或通知ID访问他人数据。

### 5.1 公共站点布局

顶部导航为“OnlyCampus Logo／发现／专栏入口／搜索／消息／个人菜单”。游客显示登录按钮；用户菜单包含创作中心、收藏和个人资料；管理员菜单显示后台入口。专栏入口可以滚动定位到首页专栏区域，无须额外开发专栏聚合页。

首页使用一张大幅精选卡配合普通文章卡片。精选不足时自然收缩版块，不生成重复文章占位。首页专栏按最近公开内容更新时间排列，不做随机推荐算法。

### 5.2 文章详情布局

桌面端主体为正文，侧栏为作者卡片和文章目录；底部展示专栏上一篇/下一篇、评论区。小屏改为单列，目录使用抽屉。正文建议宽度约720px，中文正文16—18px、行高1.7—1.9；代码块和宽表格局部横向滚动。

目录从正文二、三级标题生成；标题重复时仍生成唯一锚点。点击目录滚动到对应章节，并避免被固定导航遮挡。阅读进度只按正文区域计算，正文较短时防止除零。专注模式隐藏侧栏及非必要导航，保留退出按钮。

### 5.3 视觉规范

| 项目 | 规范 |
| --- | --- |
| 页面背景 | 米白 `#F7F5F0` |
| 卡片背景 | 白色 `#FFFFFF` |
| 正文 | 深灰 `#24312B` |
| 主色 | 墨绿 `#2F5D50` |
| 点缀 | 暖橙 `#C67840`，用于少量阶段标记 |
| 分隔线 | 浅灰 `#E5E7E3` |
| 间距 | 以4px为基准，常用8、12、16、24、32px |
| 圆角 | 输入框和按钮8px，卡片12px |
| 动效 | 150—250ms，尊重减少动画的系统偏好 |

状态同时使用文字和颜色，不能只用红绿区分。表单关联明确标签；按钮可键盘操作并显示焦点；图片有替代文本；装饰图片不重复朗读。至少验证375px手机宽度、768px平板宽度和1440px桌面宽度，无整页横向溢出。

## 6. 阅读与互动模块详细需求

### 6.1 搜索和列表

- 关键词仅搜索标题和摘要，使用参数化查询，并按字面含义处理通配符。
- 分类与标签条件同时选择时采用AND关系；每次筛选从第一页开始。
- 排序支持最新发布和最近更新，增加ID作为相同时间下的稳定次序。
- 默认每页10条，最大50条；页码和页容量必须校验。
- 只有PUBLISHED且未删除的文章可进入公开列表。
- 展示加载中、无结果、请求失败和重试按钮。
- 搜索条件保留在URL中，刷新和返回后可以复现。

### 6.2 评论与回复

评论长度1—500字，去掉首尾空白后不能为空。只允许对公开文章评论。回复只能指向同篇文章的顶层评论，不做无限嵌套。

顶层评论按创建时间倒序分页，回复按时间升序显示。本人可删除自己的评论；管理员可隐藏违规评论。被删除或隐藏的父评论保留“该评论已不可见”占位，使正常回复仍可阅读，原正文不返回公开接口。

文章下架后不能新增评论或读取公开评论列表。评论创建、回复和通知写入使用同一数据库事务，失败则整体回滚。

### 6.3 收藏

收藏接口幂等，重复收藏不会新增记录；取消收藏时记录不存在也返回成功。收藏数量以实际记录为准，不靠前端自行累加。

我的收藏允许保留下架或删除文章的占位条目，只显示“文章已不可用”和取消收藏操作，不泄露非公开正文或变更后的私人标题。公开页面不提供这些文章的访问入口。

## 7. 创作与专栏模块详细需求

### 7.1 表单规则

| 字段 | 规则 |
| --- | --- |
| 标题 | 保存草稿可为空，提交审核必须为2—80字 |
| 摘要 | 提交审核必须为10—200字 |
| 正文 | 草稿可为空；提交审核去掉空白后至少20字；最大50000字符 |
| 分类 | 提交审核必须选择1个启用分类 |
| 标签 | 选择0—5个启用标签 |
| 封面 | 可选，无封面使用统一默认样式 |
| 图片 | JPEG、PNG、WebP；单张最大5MB；校验真实内容类型并随机命名 |

不接受SVG和可执行文件。上传目录禁止执行脚本；草稿中的图片不对外单独展示业务内容。编辑器禁用原始HTML，Markdown输出经过安全过滤；链接只允许合理的网页协议。上传接口要求登录，基础版用途限制为头像和封面，正文以文本、代码块和普通链接为主。

用户点击“保存草稿”后才写入服务器，成功显示保存时间。保存失败保留当前编辑内容，允许重试。离开有未保存改动的页面时给出确认提示。不写入localStorage或IndexedDB，不做浏览器本地恢复。

### 7.2 文章状态机

| 当前状态 | 操作 | 新状态 | 操作者 | 约束 |
| --- | --- | --- | --- | --- |
| 无 | 新建 | DRAFT | 作者 | 创建本人文章 |
| DRAFT | 保存 | DRAFT | 作者 | 只允许本人 |
| DRAFT / REJECTED | 提交审核 | PENDING | 作者 | 通过提交字段校验 |
| PENDING | 撤回申请 | DRAFT | 作者 | 与审核并发时只允许一个状态变更成功 |
| PENDING | 审核通过 | PUBLISHED | 管理员 | 写审核记录和通知 |
| PENDING | 驳回 | REJECTED | 管理员 | 必须填写原因 |
| PUBLISHED | 撤回修改 | DRAFT | 作者 | 立即停止公开展示并取消精选 |
| PUBLISHED | 下架 | OFFLINE | 管理员 | 必填原因，取消精选并通知作者 |
| OFFLINE | 修改整改 | DRAFT | 作者 | 后续必须重新审核才能公开 |
| DRAFT / REJECTED / OFFLINE | 删除 | 状态保留，标记删除 | 作者 | 软删除，保留审核记录 |

PENDING状态禁止编辑；PUBLISHED状态禁止直接编辑；待审核文章先撤回才能删除，已发布文章先撤回才能删除。REJECTED状态允许编辑但保留“已驳回”状态，直至重新提交。

状态变化用事务和条件更新实现，例如仅在当前仍为PENDING时执行审核。若其他操作已改变状态，返回409并提示刷新。不能仅依赖按钮禁用避免重复操作。

`first_published_at`在首次通过审核时设置且不再改变；`published_at`记录最近一次审核发布。公开列表“最新发布”依据`published_at`，成长时间线和首次发布趋势依据`first_published_at`。

### 7.3 成长专栏

专栏字段包含名称、简介、封面和公开开关，名称2—40字，简介不超过300字。一个专栏最多50篇文章，一篇文章最多归属一个专栏，降低章节导航复杂度。

作者只能选择自己的未删除文章加入专栏，可包含草稿以便提前编排。管理页显示所有已关联文章及状态；公开页仅显示PUBLISHED文章。专栏设置公开且至少有1篇公开文章时，才能进入首页和作者主页。

章节排序通过“上移／下移”实现，保存时提交完整文章ID顺序；服务端检查归属、重复ID和文章集合一致性后以事务更新。阶段标签可选“起步、实践、成果、复盘”，不强制各阶段齐全。

目录视图依据章节顺序，时间线视图依据首次发布时间升序，时间相同时按ID排序。上一篇、下一篇始终依据章节顺序，仅链接公开文章。专栏文章数及更新时间仅计算公开文章，不能暴露草稿数量或草稿修改时间。

删除专栏只移除专栏及关联，不删除文章。隐藏专栏不影响其中文章独立公开。

## 8. 审核与平台管理详细需求

### 8.1 审核工作台

列表支持按状态、作者和标题查询。详情采用文章预览与处理面板分栏，显示作者、提交时间及历史审核记录。

审核通过可以填写备注；驳回和下架必须填写2—300字原因。每次状态变化记录操作者、原状态、新状态、操作时间和原因。管理员不可在审核界面修改正文。

仅公开文章可设置精选；首页最多展示4篇精选，设置第5篇时提示先取消已有精选。文章撤回、下架或删除时同步取消精选。

### 8.2 用户、分类、标签和评论治理

- 用户列表展示昵称、账号、角色、注册时间、账号状态，不返回密码哈希。
- 禁用用户填写原因，禁用和恢复操作写入管理日志。
- 分类与标签名称去除首尾空白后唯一；允许调整名称、排序和启用状态。
- 已被文章引用的分类和标签不可物理删除，可停用。停用后旧文章仍保留显示，新提交文章不得选用；公开筛选仍可访问有公开文章的历史分类。
- 违规评论隐藏时保留原记录供后台查看，填写原因并记管理日志；本人删除的评论不允许管理员恢复公开。

### 8.3 数据概览和近7日发布趋势

后台显示注册用户数、当前公开文章数、当前待审核数、当前可见评论数。管理员账号不计入注册用户数，软删除文章不计入当前文章指标。

近7日按Asia/Shanghai自然日统计，包含今天，缺失日期补0。趋势统计“每天首次发布的文章数”，每篇文章仅计一次，重新审核通过不重复计数。

首次发布成功时，向发布事件表写入唯一记录。后续文章下架或软删除不抹去历史事件，因此该趋势与当前公开文章数不要求相等。图表标题和说明必须明确这一口径。

图表展示日期横轴、篇数纵轴、整数刻度和提示信息，下方附相同数据的简表。全部为0时正常展示并说明暂无首次发布记录，不用虚构曲线填充。

### 8.4 站内通知

| 触发事件 | 接收人 | 内容与目标 |
| --- | --- | --- |
| 顶层评论成功 | 文章作者，排除自己评论自己 | 评论人、简短摘要、文章评论位置 |
| 回复成功 | 被回复的顶层评论作者，排除自己回复自己 | 回复人、简短摘要、文章评论位置 |
| 审核通过或驳回 | 文章作者 | 处理结果、原因摘要、作者工作台文章详情 |
| 管理员下架 | 文章作者 | 下架原因、作者工作台文章详情 |

一次回复只通知被回复人，不再重复通知文章作者。基础交付不包含评论点赞通知、收藏通知和管理员待审核提醒。

通知列表每页10条，支持全部、未读以及类型筛选；提供单条已读和全部已读操作。点击通知后标记已读并尝试跳转；若文章、评论已不可用，保留通知并提示目标不可用。只有接收人可查询及修改自己的通知。

通过进入页面、完成相关操作以及页面可见时每60秒刷新未读数，不使用WebSocket。未登录、退出或页面不可见时停止轮询。此方案是站内消息中心，不承诺实时推送。

通知在业务事务内写入，事务失败不留下成功通知。每条通知使用唯一事件键防止同一次业务操作重复产生记录，通知文本不包含文章完整正文。

## 9. 数据库设计

所有主键采用BIGINT，接口统一返回字符串ID，避免JavaScript大整数精度问题。数据库连接时区统一为UTC，接口日期使用带时区的ISO 8601字符串；展示和日统计使用Asia/Shanghai。字符集采用utf8mb4。

### 9.2 关系说明

- 用户与文章、专栏、评论均为一对多。
- 分类与文章一对多，标签与文章多对多。
- 专栏与文章通过关联表记录顺序，业务上限制一篇文章最多一个专栏。
- 用户与文章通过收藏表构成多对多。
- 文章与审核记录、评论一对多，与首次发布事件一对一。
- 通知属于一个接收人，文章、评论和审核记录引用根据类型可为空。

### 9.3 索引与一致性

- 文章索引：`(status, published_at, id)`、`(author_id, status)`、`category_id`。
- 评论索引：`(article_id, parent_id, status, created_at)`。
- 通知索引：`(recipient_id, read_at, created_at)`。
- 审核记录索引：`(article_id, created_at)`。
- 发布事件索引：`first_published_at`。
- 收藏以`(user_id, article_id)`作为唯一约束。
- 审核状态修改、审核记录、首次发布事件和通知必须在同一事务中完成。
- 评论创建和通知必须在同一事务中完成。
- 不维护容易失真的手工文章数、收藏数副本，课程规模内通过查询统计。
- 文章软删除；普通业务接口不物理删除用户，保证历史引用完整。

## 10. 接口约定

统一前缀`/api`，请求及响应使用JSON；上传使用multipart/form-data。写操作验证Session与CSRF令牌，同源部署也不能省略必要的请求来源和CSRF检查。

成功响应：

```json
{
  "code": "OK",
  "message": "操作成功",
  "data": {}
}
```

分页data统一为`items、page、pageSize、total`。错误响应包含稳定的业务code和中文message，表单错误可提供fieldErrors。不要向客户端返回SQL或异常堆栈。

| HTTP状态 | 使用场景 |
| --- | --- |
| 400 | 参数格式错误 |
| 401 | 未登录或会话失效 |
| 403 | 已登录但无操作权限、CSRF校验失败 |
| 404 | 不存在或公开访问不可见的资源 |
| 409 | 状态冲突、重复名称、编辑版本已变化 |
| 422 | 表单业务校验失败 |
| 429 | 登录或评论频率过高 |
| 500 | 服务端异常，显示通用失败信息 |

2. 柏承辰保存评论并调用赵庆浩的通知服务。
3. 用户甲收到未读通知，点击进入文章对应评论位置。
4. 用户甲回复用户乙的顶层评论，用户乙收到回复通知。
5. 作者给自己的文章评论、用户回复自己时不创建通知。

### 11.3 下架与跨页面一致性

1. 管理员填写原因并下架文章。
2. 首页、搜索、作者主页和公开专栏不再显示该文章。
3. 直接访问公开详情返回不可用提示，不能评论或新增收藏。
4. 已有收藏保留失效占位；旧通知允许读取但不能绕过文章权限。
5. 作者在工作台查看原因，整改、提交、再次审核通过后重新公开。
6. 历史首次发布趋势不增加第二次记录。

### 14.1 演示数据

## 16. 前端设计技能安装与使用

三名成员在各自电脑安装下列 Codex 技能，供后续前端设计、实现和审查时使用。安装只作用于各自账户，不会随项目文件自动同步；功能和视觉方案仍以小组讨论及本文约定为准。

| 技能 | 来源 | 用途 |
| --- | --- | --- |
| design-taste-frontend | [taste-skill](https://github.com/Leonxlnx/taste-skill) | 页面艺术方向、布局和浏览器视觉检查 |
| impeccable | [impeccable](https://github.com/pbakaus/impeccable) | 交互、排版、响应式及设计质量审查 |
| ui-ux-pro-max | [ui-ux-pro-max-skill](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill) | 查询设计风格、配色、可访问性和技术栈建议 |

### 16.1 在 Codex 中安装

最简单的方式是在自己的 Codex 会话中直接发送以下请求，让 Codex 使用其 `skill-installer`：

```text
请安装以下 GitHub 技能到我的 Codex 用户技能目录：
Leonxlnx/taste-skill 的 skills/taste-skill，安装名 design-taste-frontend；
pbakaus/impeccable 的 .agents/skills/impeccable，安装名 impeccable；
nextlevelbuilder/ui-ux-pro-max-skill 的 .claude/skills/ui-ux-pro-max，安装名 ui-ux-pro-max。
请检查 ui-ux-pro-max 的 SKILL.md 中 Claude 插件专用路径，并改为指向安装后的技能目录。
```

也可在 Windows PowerShell 中执行以下命令，要求已安装 Python，且 Codex 自带 skill-installer 脚本。路径中的 `$env:USERPROFILE` 会指向当前成员自己的用户目录。若技能目录已存在，安装器会停止，先检查已有版本，避免覆盖个人修改。

```powershell
$installer = "$env:USERPROFILE/.codex/skills/.system/skill-installer/scripts/install-skill-from-github.py"
python $installer --repo Leonxlnx/taste-skill --path skills/taste-skill --name design-taste-frontend
python $installer --repo pbakaus/impeccable --path .agents/skills/impeccable --name impeccable
python $installer --repo nextlevelbuilder/ui-ux-pro-max-skill --path .claude/skills/ui-ux-pro-max --name ui-ux-pro-max

# 修正上游 Claude 插件路径，使 Codex 以技能目录为基准调用脚本
$skillFile = "$env:USERPROFILE/.codex/skills/ui-ux-pro-max/SKILL.md"
$content = Get-Content -LiteralPath $skillFile -Raw -Encoding UTF8
$content = $content.Replace('${CLAUDE_PLUGIN_ROOT}/.claude/skills/ui-ux-pro-max', '<skill-base-dir>')
[IO.File]::WriteAllText($skillFile, $content, [Text.UTF8Encoding]::new($false))

# 验证数据和搜索脚本可运行
python "$env:USERPROFILE/.codex/skills/ui-ux-pro-max/scripts/search.py" "campus blog" --design-system -p OnlyCampus
```

`<skill-base-dir>` 是文档中的占位符，使用时替换为安装后的 `ui-ux-pro-max` 目录。安装后开启新的 Codex 会话，使新技能被发现；可通过技能列表或在新会话中要求 Codex 列出上述技能来检查。GitHub 仓库持续更新，如路径失效，以对应仓库当前 README 为准，并同步组员。

### 16.2 使用约定

- taste-skill 的仓库说明要求 Node.js 22 及以上和本机 Chrome、Edge 或 Chromium；视觉检查时根据实际环境运行。UI/UX Pro Max 的本地查询脚本需要 Python 3。
- impeccable 此处安装的是技能目录，**不包含其可选自动检查 hook 或子代理**。如需要 hook，参考仓库官方安装说明，先了解其行为，再按 Codex 的 `/hooks` 授权流程启用；不把 hook 当作本课程的必需条件。
- 制定首页与文章阅读视觉方向时，可让 Codex 调用 `design-taste-frontend`；完善交互、响应式和无障碍时调用 `impeccable`；需要参考配色、字体或布局模式时调用 `ui-ux-pro-max`。
- 示例提示词：“使用 design-taste-frontend 和 impeccable，为 OnlyCampus 的首页设计并实现符合项目视觉规范的页面；完成后检查桌面和手机布局。”也可按任务实际需要只调用其中一个技能。
- 技能提供设计建议，不直接替代小组的业务约束、权限规则、可访问性检查或实际浏览器验收。若技能建议与本文已商定规范冲突，由三人讨论后统一修改，不让三个模块各自形成不同风格。
